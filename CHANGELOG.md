# Changelog

All notable changes to Faultline Pro are documented here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

> **Release stage: alpha.** Usable today, with sharp edges. Verdict accuracy has not yet been measured on a labelled test set, and anything may change before 1.0.

## [Unreleased]

### Added

- **Read-only keystore audit (`fly-ops.yml`, action `keystore-audit`).** Reads `/var/log/faultline/keystore.json` on the Fly machine and prints one JSON line of counts, lengths, known field names, the file mode and a 12-character hash head per key, never a key, hash or other file content; it counts any 64-hex string outside the record hash fields. Docs: `docs/runbooks/fp-operating-runbook.md` (Keystore).
- **Hosted MCP endpoint at `POST /mcp`.** An MCP client can list and call `verify_claims` on the API with a Faultline API key (`x-api-key`) and nothing installed. Streamable HTTP transport, stateless: a new server and transport per request, no session id, JSON responses; `GET` and `DELETE /mcp` answer `405` with `Allow: POST`. The tool is built from `packages/mcp`'s own definition (`buildServer` now takes the scan transport as an argument), so the stdio and hosted tools are the same name, input schema, descriptions and output; a test checks that their `tools/list` answers are equal. Every call scans through the API's own `POST /scan` in-process with the caller's key and no other header, so the burst limit, monthly quota, provider spend cap, claim meter and caps, the zero-source rule, `overallRisk` and `billing` are the `POST /scan` code path; the tool result carries `overall_risk` and `billing`, and a refusal (`402`, `429`, `503`, ...) comes back as an MCP tool error that says nothing was checked. A missing or invalid key gets `401` with a JSON-RPC error body before any MCP processing. A request with an `Origin` header is refused with `403` unless the origin is listed in `FAULTLINE_MCP_ALLOWED_ORIGINS` (empty by default); no `Origin` is allowed. The measurement key is refused. The hosted server writes no audit file. The image now installs `packages/mcp` and its SDK, and a change under `packages/mcp` triggers the API deploy. Docs: `docs/INTEGRATION.md` §13.
- **The CLI and the MCP server say what a 401, 402, 403 or 429 from the hosted API means.** Each carries the API's own error body (for example `consensus_not_in_plan`, or the burst limit's `limit`, `remaining` and `resetEpoch`) and says nothing was verified and it is NOT a verdict on the claims; a `402` reads as "no quota left for this scan".
- **Agents can discover the API.** Three new public routes, no key: `GET /openapi.json` (the OpenAPI 3 document `@fastify/swagger` builds from the live routes, the same as `/docs/json`), `GET /llms.txt` (a plain-text guide to the API: base URL, `x-api-key`, main endpoints, verdicts, the billable-claim rule) and `GET /pricing` (10 USD a month including the first 100 billable claims, then 0.10 USD per billable claim; claim caps of 100, 1,000 by default, and 10,000 claims a month; whether an unverified verdict bills, read from the engine's `isBillableVerdict`). A root `server.json` describes Faultline for the official MCP Registry as a remote-only server (`ai.nxtg/faultline`, one Streamable HTTP remote at `https://faultline-api.fly.dev/mcp`, a required, secret `X-API-Key` header); it is not published to the registry yet.
- **API keys survive a deploy and are stored only as hashes.** Issued keys (`POST /keys`, `POST /orgs/:id/keys`, GraphQL `createKey`) were held in memory with their plaintext, so every deploy or restart deleted them all, and a memory dump showed live keys. The keystore now keeps a SHA-256 of each key (and of the replaced key during the 24-hour rotation grace), never the key, and checks a presented key by hashing it and comparing in constant time. It is written to `keystore.json` on the ledger volume, beside the Idempotency-Key ledger (`FAULTLINE_KEYSTORE_FILE` overrides; `off` keeps it in memory), as one JSON file replaced atomically on every change (temp file, mode 0600, fsync, rename), and loaded at startup with every field a key has, so a key behaves the same after a restart, claim cap and meter included. `lastUsedAt` alone is written at most once a minute. A keystore file that cannot be read or parsed starts the server with no issued keys (they do not authenticate) instead of crashing, and a failed write keeps serving from memory; admin `GET /usage` counts both under `keystore` (`loadFailures`, `writeFailures`, with `idempotencyWriteFailures`), and each logs one fixed line without key material. The plaintext is still returned once, by the create and rotate responses. Responses that describe a key now carry `keyPrefix` (first 8 characters), and the rotate response's `previousKey` is the replaced key's prefix instead of the full old key. The environment keys (admin, server and measurement) are unchanged. No migration: keys made before this deploy were in memory and do not exist after it.
- **Weekly provider cost and claims by key class.** Every provider-spend row now carries `keyClass`: `customer` (a keystore key without `admin`), `internal` (the server key and keystore keys with `admin`), `measurement` (the measurement key) or `anonymous` (no key). It is set where the row is built, from the authenticated key, on every path that writes a spend row (every scan route and background runner, the full-scan estimate and job, critique and admin verify), and is a class, never a key id. A full-scan estimate's row also carries `stage: "extraction"`. New admin-only `GET /admin/cost-summary?from=&to=` (default: the last complete Monday 00:00Z to Monday 00:00Z week; 403 for every non-admin key, the measurement key included) sums, per key class, `costUsd`, `calls`, `claimsHandled` and `billableClaims` from the spend ledger over the window, and reports `customerBilledClaims` from the usage record (void rows excluded) and `customerUnbilledClaims`. Rows written before this change read as `unlabelled`. New `scripts/cost-scoreboard.mjs --out <path>` writes that JSON and prints the cost per billed customer claim. Billing, verdicts and the spend cap are unchanged.

- **Every scan or verify result says which claims were not billed, and why.** A claim is billed only when it gets a supported, contradicted or mixed verdict with at least one source. Unverified claims, claims with no source and claims where the provider failed are not billed. Each result's `billing` field lists them with the reason. `billing` is on the result of `POST /scan` (also `POST /scan/template/:id`), `POST /scan/deep`, the `complete` event of `GET` and `POST /scan/stream`, `GET /scan/full/:jobId` (and its `/stop`) once the job has a result, and `POST /admin/verify-claims` (beside `results`). It reads `{ "billedClaims": 1, "unbilledClaims": 2, "unbilled": [{ "claimId": "c2", "reason": "unverified" }, { "claimId": "c3", "reason": "no_source" }] }`. The reason for each unbilled claim is the first that applies: the provider failed (its `apiErrorReason`, such as `rate_limited` or `timeout`, else `provider_error`); `no_source` (no source a reader can open, so the verdict was reported as unverified); the verdict itself when it is not supported, contradicted or mixed (`unverified`, `skipped`); `no_source`; `no_retriever` (the sources were not retrieved by the engine, the mock provider for one). It is computed from the verifications you are given, so a cached result carries it too, and `billedClaims` is the number the claim meter commits for that result. It only reports billing: what is billed is unchanged.
- **A claim list with an over-long or repeated claim id fails extraction.** An extracted claim id longer than 58 characters (the claim meter's limit, now one shared constant), or one that repeats an earlier claim's id (a numeric id counts as its string form), or the id `__proto__` (which would set a plain object's prototype instead of adding an entry), fails the extraction with `invalid_output`, the same error as any other malformed claim list (`502 extraction_failed` on `POST /scan`, an `extraction_failed` error event on `/scan/stream`). Before, billing counted such a claim while the meter committed a different number. Synthetic per-sentence claim ids no longer reuse an id already in the scan.
- **Non-admin keys are metered by default at a 1,000-claim cap.** Every non-admin key issued from now on (`POST /keys`, `POST /orgs/:id/keys`, GraphQL `createKey`) gets `metered: true` and `claimCap: 1000` (100 USD a month at 0.10 USD per billable claim) unless the request sets them; `metered: false` needs an admin caller. A non-admin key's `claimCap` must be an integer from 100 to 10,000 on create and on `PATCH /keys/:id` (`400 claim_cap_out_of_range`); a numeric string cap is coerced like every other field (`"500"` is 500) and the rule is on the coerced value; and a metered non-admin key's cap cannot be cleared (`400 claim_cap_required`). Admin keys, the server key and the measurement key are unchanged and never metered by default. The meter still runs only with `FAULTLINE_CLAIM_METER=1`.
- **A separate measurement key, labelled on spend rows and limited to admin verify and usage.** Internal measurement runs no longer need the server key that faultline-web uses. A new optional `FAULTLINE_MEASUREMENT_KEY` authenticates as keyId `measurement` (constant-time; an empty value never matches; a value equal to `FAULTLINE_API_KEY` is ignored, with one fixed startup warning). It may call only `POST /admin/verify-claims` and `GET /usage`; every other route, admin or not, answers it 403, from one allowlist (`MEASUREMENT_ROUTES`). It is not the server key, so its `x-user-tier` is ignored, and every tier resolver labels it `measurement`: its provider-spend ledger rows, scan-cost log rows and cost-store events carry tier `measurement`. `GET /usage` shows it `providerBudget` and `groundingAllowance`; the fleet spend cap never refuses it; its burst limit is 600 per minute. The Accuracy G0 workflow (repo secret `FAULTLINE_MEASUREMENT_KEY`) and `scripts/measure-cost-per-claim.mjs` (env or `~/.config/faultline/measurement-key.env`) use it when set and otherwise fall back to the admin key with a printed warning that the run is not labelled; their client-side spend caps are unchanged. Accuracy G0 in branch mode does not use it: neither the branch engine nor the branch runner step gets the measurement key, so a branch run sends the admin key and the branch engine's USD 28 spend cap still stops it, as before. Both runners read the public `GET /health` with no key header (the measurement key gets 403 there), so the engine identity they record is the one `/health` returns. Scan-cost log rows with tier `measurement` survive a reload of the cost store; `x-user-tier: measurement` is still not forwardable. `fly-ops.yml` gains `measurement-key-set` (from the repo secret, through env; an empty secret fails and changes nothing) and `measurement-key-unset`. Verdicts, confidence, sources, prompts and models are unchanged.
- **Cost per claim reads straight off either ledger.** Every `scan-cost.jsonl` row carries `claim_count` and `verified_count`, and every `provider-spend.jsonl` row now carries `claimCount` and `verifiedCount`: claims the call handled and claims that got a billable verdict (supported, contradicted or mixed, with at least one source, and not an `apiError` claim; `unverified` and zero-source verdicts are not counted). `POST /critique`, which handles no claims, writes `0` and `0` on its spend row. The cost event builder requires the counts, so a new spend path cannot leave them out. Old rows without the fields still load and still count toward the monthly spend total. Pricing, the cap, verdicts and prompts are unchanged.
- **G0 can measure a branch before it deploys.** The Accuracy G0 workflow takes `engine: branch`: it starts the API from the dispatched ref on the runner and runs the pre-registered set against it. The daily 1,000 grounded-prompt guard adds production's count, because both engines use the same Google key (`--allowance-api`, with 100 prompts left for production; one branch run per Pacific day; branch engine spend cap USD 28; no raw server log in the artifacts; six new runner tests). Needs the repo secret `FAULTLINE_G0_GEMINI_KEY`. GoPMO 1.18.11.7.18 A0.
- **Per-key claim cap and the usage record, behind `FAULTLINE_CLAIM_METER=1` (off by default, so nothing changes until it is switched on).** Keys gain `metered`, `claimCap`, `stripeCustomerId` and `scopes`; only `metered: true` keys are metered. The billable unit is one claim the engine's `isBillableVerdict` accepts: `supported`, `contradicted` or `mixed`, with at least one source, an engine-set `provenance.retriever`, and not an API error; `unverified`, unsourced and retriever-less verdicts are never billed, and the usage record refuses a row with any other verdict. The measurement key, like admin keys and the server key, is never metered. Every verifying route reserves before any provider call and answers `402 claim_cap_reached` (`cap`, `used`, `remaining`, `period`, `resetsAt`) or `402 claim_cap_unset`. Committed claims go to an append-only record with a gap-free `seq`, read by the billing side from `GET /admin/usage-records` (scope `usage:read`, header `X-Usage-Record-Version: 1`); admin `GET /usage` adds `usageRecords`. A full-scan job whose verdicts were lost before its owner saw them gets void rows. `POST /keys` accepts `Idempotency-Key`. This API makes no Stripe call.
- **Exports carry who checked each claim, when, and what the sources said.** SARIF verification results (`properties.provenance`, `properties.sources[].evidence`, `properties.independentEvidence`), `faultline guard --json` (per claim `status`, `provenance`, `sources`, `independent_evidence`; `verdict` keeps the `--fail-on` vocabulary) and the `faultline export` CSV (seven columns appended after the existing ones: `checked_by_provider`, `checked_by_model`, `verified_at`, `retriever`, `retrieved_at`, `evidence_json`, `independent_evidence_json`). The `guard` table now prints the engine's verdict word (SUPPORTED, CONTRADICTED, MIXED, UNVERIFIED, NOT CHECKED) and a "checked by" line, never "VERIFIED". The API's `/export` CSV holds per-scan summaries without verdicts, so it is unchanged. (emma-soul al:193832a732e0b82e item 6, GoPMO 1.18.11.3)
- **Evidence fetches honour robots.txt.** Before the API reads a cited page, or follows a redirect to another page, it asks that site's robots.txt (RFC 9309) whether `FaultlineEvidence` may read it. A disallowed page is never requested and its source carries `evidence` `{status: "not_fetched", reason: "robots", passage: null}`; the API PDF prints "Passage not retrieved (site's robots.txt)". Every fetch, robots.txt included, sends `User-Agent: FaultlineEvidence/1.0 (+https://faultline.nxtg.ai)`. Each site's answer is cached for 24 hours (1 hour when robots.txt cannot be read; then nothing on that site is fetched, and the source reads `fetch_failed`). A hostile robots.txt cannot stall the API: rules are matched without regexes under a fixed work budget. A stored passage is now at most 300 Unicode code points (was 400 characters), cut between whole characters. OpenAI's terms clear our use of a search result's URL, not the publisher's page, which each site governs. (emma-soul al:15b443bc1ccf7a4e, GoPMO 1.18.11.3)
- **Evidence passages read as prose.** A quoted passage must be a sentence of at least 40 characters and six words, never navigation crumbs, JSON or wiki template text, and must share at least half of the claim's content words; a number from the claim (a year, a figure) counts double, so the sentence carrying it wins. Found on the first live run of the passage leg, where a site's breadcrumb and a Wikipedia template blob had been quoted. (GoPMO 1.18.11.3)
- **Independent passages beside a Gemini verdict (behind `FAULTLINE_PASSAGE_LEG=on`, off by default).** Since Gemini grounding Links may not be fetched, the API can run OpenAI web_search on each verified claim, fetch that search's own result pages (at most 3, through the guarded fetch) and quote the best-matching passage from each into `independentEvidence` `{retriever, model, retrievedAt, sources}`. It is kept apart from the verdict's `sources`, and the search model's own snippets are never carried as evidence. Default model `gpt-4o-mini`, measured at about 1.1 to 1.3 cents per claim. The API PDF prints these passages under their own heading. The spend ledger now prices a gpt-4o-mini web_search call with its 1 cent fee. (GoPMO 1.18.11.3; emma-soul authorization)
- **Gemini grounding Links are never fetched for evidence.** Google's grounding terms forbid "using Links to identify destination pages for crawling or scraping". A source cited by Gemini Grounding with Google Search now carries `evidence` `{status: "not_fetched", reason: "provider_terms", passage: null}` and no request is sent; links from other retrievers are still fetched and quoted. This narrows the evidence-passage change below the same day it shipped (emma-soul ruling, GoPMO 1.18.11.3).
- **Evidence passages from the fetched page.** On the hosted API (`POST /scan`, `/scan/stream`, full scan, template scans), each cited source carries `evidence` `{status, passage, fetchedAt, finalUri?, httpStatus?, contentSha256?, truncated?}`. The API follows the cited link (Google's grounding redirect to the publisher), refusing private addresses at every hop, reads at most 1.5 MB within 6 seconds, and quotes the sentence that best matches the claim from the page's own text. When nothing matches it says `no_match` and quotes nothing; it never uses the model's words as evidence. The API PDF prints each passage with the time the page was read. `FAULTLINE_EVIDENCE_FETCH=off` turns the fetch off. (GoPMO 1.18.11.3 P1b; EP4 recert evidence row 3)
- **Every verdict names who checked it and when.** A verdict whose check ran carries `provenance` `{provider, model, verifiedAt, retriever?, retrievedAt?}`, bound at the provider call. The provider id is the one the engine resolved, so a provider cannot claim to be another. Gemini reports the model Google served (`modelVersion`) and one time for retrieval and verdict, since a grounded request searches and judges in one call. Consensus lists each voter's `name:model`, its retriever and when the shared retrieval returned. A verdict whose check never ran carries none. The API PDF prints a "Checked by" line per claim and each source's URI, and the claim index records a source's `seenAt` as the evidence retrieval time when the verdict carries one. (GoPMO 1.18.11.3 P1a; EP4 recert evidence rows 2-3)
- **Verdict states are enforced at runtime, not only typed.** Every verdict is checked against an allowlist (`supported`, `contradicted`, `mixed`, `unverified`) and a shape (string explanation, sources with string `uri`) as it leaves the verifier. A verdict that fails becomes `unverified` with `apiError: true` and `apiErrorReason: "provider_error"` (a full scan refunds it) and never carries the bad value. The API's scan store, scan cache and claim index, and the CLI's disk history, refuse a result whose status is outside the stored allowlist (the four verdicts plus `skipped`); the full-scan job store replaces such a verdict with an unserved, refunded one; and `POST /scan` answers `502 invalid_verdict` before storing or caching anything. (GoPMO 1.18.11.3 P2; EP4 recert evidence row 1)
- **Google Search Suggestions on every grounded verdict.** A verdict from Gemini with Grounding with Google Search now carries `searchEntryPoint.renderedContent` and `webSearchQueries` from its own grounded request, unaltered, on `GET`/`POST /scan/stream`, `POST /scan` and full-scan `GET`. Google's grounding terms require the suggestion to be shown wherever the grounded result is shown; faultline-web renders it. Never written to any ledger. (GoPMO 1.18.11.3; fw al:da4e96a09515f831)
- **Daily revenue scoreboard read into the Dx3 ledger** (`scripts/scoreboard-read.sh`, user timer `fp-scoreboard-read.timer` at 22:15 America/Chicago, GoPMO 1.18.11.1.7). It runs the Stripe oracle pinned at dcc3bff (sha256 checked) and dx3's writer pinned at 6536eb9, both from git objects, and the writer reads the row back. Only aggregate counts are written; the key stays in fp's key file.
- **`POST /admin/verify-claims` (admin key only)** verifies up to 25 claims as given, with no re-extraction, through the same `verifyClaim` a scan uses, behind the burst limiter and the provider-spend cap, with usage priced into the same spend and grounding ledgers. It returns status labels and flags only (`status`, `apiError`, `parseFallback`, `model`), never explanations or sources. It exists for the pre-registered verdict-accuracy run (`docs/research/accuracy-g0-harness.md`); `GET /health` now also reports the build `commit` so that run can show the engine did not change.
- **Engine: full scan mode ("deep scan" in product copy).** `scan(..., { mode: 'full' })` verifies every claim of type `fact`, any importance, in extraction order, and ignores the verify cap; opinions and interpretations are never sent to verification and are listed as `verification.notCheckableClaimIds`. The full-mode `verification` adds `mode`, `factClaims`, `servedClaims` (got a billable verdict: supported, contradicted or mixed, with a source, no API error) and `unservedClaimIds` (started without one: a provider error, including a provider that failed every retry, or an `unverified` or zero-source verdict). `extractForFullScan(text)` extracts and prices a full scan (`units = ceil(factClaims / 8)`) with no verify call; `verifyFullScan(claims, { onClaim, signal })` verifies exactly those claims with per-claim progress and reports claims a stopped run never started as `notAttemptedClaimIds`; `unitAccounting(charged, servedClaims)` gives `{ charged, served, refund }`. Quick scans are unchanged. Spec: `docs/design/2026-10-13-full-scan-api.md` section 2.
- **Full scan API ("deep scan"): `POST /scan/full/estimate`, `POST /scan/full`, `GET /scan/full/:jobId`, `POST /scan/full/:jobId/stop`.** The estimate extracts claims and prices the scan at one unit per 8 factual claims before anything is charged, and lists the factual claims it priced. The run checks exactly those claims, 4 at a time, and the job is polled for per-claim verdicts as they land. A claim is served only when its verdict is billable (supported, contradicted or mixed, with at least one source, and not an API error); every other claim is refunded with a reason code: `rate_limited`, `provider_unavailable`, `timeout`, `provider_error`, `provider_unparseable`, `output_truncated`, `no_sourced_verdict` (the check ran but returned `unverified` or no source) or `not_attempted` (never started because the job was stopped). Starting is idempotent on `Idempotency-Key`; one active job per user (`x-faultline-user-ref`, honoured only from the web app's server key); at most 4 jobs run at once, the rest queue. Finished jobs are recorded on the ledger volume without any text, claim or source, so a deploy does not lose their units; admin `GET /usage` reports the 7-day refund rate (`fullScanRefunds`, alert above 10%), and the hourly check alerts on a refund rate above 10% or a failed ledger write. A job whose record failed to write says `durable: false`, so faultline-web settles on the answer it has instead of a later `job_lost`; `Idempotency-Key` must be a plain 8-128 character token. A new job is refused with `503 ledger_unavailable` while the job ledger cannot be written: each admission makes a real non-empty write, and after any failed ledger write a breaker refuses new jobs and finishes queued ones unrun (fully refunded) until an 8 KB probe row reaches the disk. faultline-web's meter performs the charge and refund. Contract: docs/design/2026-10-13-full-scan-api.md.

### Changed

- **The fleet provider-spend cap refuses free and anonymous traffic only, and the budget alert fires at 90%.** With enforcement on and the month's budget spent, `enforceProviderSpendCap` answers `503` only for the `free` and `anon` tiers; `personal`, `pro` and `enterprise` pass it and stay bounded by the burst limiter and the monthly scan quota. The tier comes from `resolveSpendCapTier` (built on `resolveEntitledTier`): `x-user-tier` counts only from the server's own key, so a free key sending `x-user-tier: pro` is still refused, a server-key request with no or an empty `x-user-tier` counts as `free`, and a server-key request forwarding `x-user-tier: userkey` counts as `free` too, because no provider key can be brought through the API. `GET /usage` (admin) adds `providerBudget.appliesTo: ["free", "anon"]`. `scripts/grounding-allowance-check.mjs` alerts once per budget month at 90% of the cap and once more at 100%, and treats a `/usage` reply with no `providerBudget` as a probe failure (exit 2). Enforcement stays off by default.
- README: removed the NIST AI RMF and ISO 42001 mapping claim and the 'audit-grade' label; no shipped artifact supports them.
- **Every model call has an output-token ceiling, and a reply cut off at it is never a verdict.** Each request now carries a limit from one table (`packages/cli/providers/call-ceilings.ts`, values and their basis in `docs/cost-ceilings.md`), sized from a sample run on 2026-10-21: Gemini also gets a thinking budget (extract 2048 thinking / 34816 total; grounded verify, retrieve and shared-source judge 4096 / 5120; critique 4096 / 6144), OpenAI Chat `max_completion_tokens` and Claude and Perplexity `max_tokens` (verify 1024, critique 2048, extract 16384), the OpenAI web_search retriever `max_output_tokens` 2048. Claude's flat `max_tokens: 4096` on every call is gone; Gemini, OpenAI and Perplexity had no limit. A reply that stopped at its ceiling (Gemini `MAX_TOKENS`, Chat `finish_reason: "length"`, Responses `incomplete` at `max_output_tokens`, Claude `stop_reason: "max_tokens"`) makes a verify claim unchecked with `apiErrorReason: "output_truncated"` (`status: "unverified"`, `apiError: true`, no sources, unbilled and never cached, like `provider_unparseable`), fails an extraction with reason `output_truncated` (API `502 extraction_failed`) instead of returning fewer claims, and counts as a failed retrieval or a failed critique. MCP and `faultline guard` report `UNCHECKED` with `unchecked_reason: "output_truncated"`; a full scan refunds it under `fullScanRefunds.reasons.output_truncated`; consensus carries the reason when every failed vote shares it. Prompts, models and temperatures are unchanged. A G0 run on the branch validates the ceilings before deploy; it had not run when this entry was written. (GoPMO 1.18.11.7.18)
- **Verify prompts back to the measured wording; the no-source backstop stays.** The prompt rule below lowered balanced accuracy from 0.763 to 0.691 and passed more false claims (30 to 40), so every verify prompt is back to the `47b72f0` wording; the grounded Gemini backstop (`contradicted` with no grounding source becomes `unverified`, `noSourceAbstain`) and `provider_unparseable` stay. A test pins each verify prompt's sha256: a prompt or verdict-logic change is measured on G0 on a branch before deploy. (ruling Dx3 67cd2d8b)
- **Absence of evidence is `unverified`, never `contradicted`** (prompt part reverted, see above). Every verify prompt (Gemini grounded, Gemini and shared consensus prompts, OpenAI, Claude, Perplexity) now defines `unverified` and states that `contradicted` needs a source (or, without search, knowledge) that the claim is false. On the grounded Gemini path, a `contradicted` reply with no grounding source at all is reported as `unverified` and marked `noSourceAbstain: true`; `POST /admin/verify-claims` and the G0 runner carry that flag so the accuracy run can count it. Found on a production scan where a true court fact came back contradicted with "No search results were found" (fw al:3dc2e0b227eaedd6); the G0 run on `47b72f0` answered `unverified` once in 661 claims. The G0 re-run on `3565df7` measured balanced accuracy 0.691 [0.648, 0.734] (was 0.763 on `47b72f0`): fewer true claims shown as contradicted (36 to 23), more false claims passed as supported (30 to 40) (`docs/research/2026-10-16-accuracy-g0-rerun-3565df7.md`). (ruling Dx3 d8f5c369)
- **An unreadable provider reply is no longer a verdict.** When a provider's verify reply is not JSON, or carries no status from the prompt's list (`supported`, `contradicted`, `mixed`, `unverified`), the claim is now unchecked: `status: "unverified"`, `apiError: true`, `apiErrorReason: "provider_unparseable"`, `parseFallback: true`, no sources and no provenance. Before, Gemini reported prose as `mixed` and every provider reported JSON without a status as a plain `unverified`, so the user saw a verdict no provider gave and the claim was billed. It now counts as degraded, is never cached, is refunded on a full scan (`fullScanRefunds.reasons.provider_unparseable`) and is free on every meter that skips `apiError`; the MCP and `faultline guard` surfaces report `UNCHECKED` with `unchecked_reason: "provider_unparseable"`. Consensus votes with an unreadable reply count as failed votes. `POST /admin/verify-claims` now reports such a claim as `apiError: true` (it was `mixed`), so a G0 re-run scores it as a failure, not an abstention. (emma-soul ruling al:5b18840b0116047a item c)

- **The verification cap is a per-plan server-side setting, 8 on every plan, so results and cost per scan are unchanged.** A scan still verifies at most 8 claims (facts of importance 2 or higher, most important first). ### Fixed

- **An unverified claim is never read as low risk.** A claim that comes back unverified (no source found, a provider error, or never checked) means its risk was not checked. Before this fix the overall risk counted only contradicted and mixed verdicts, so a scan whose claims all came back unverified, such as a draft built on made-up citations that no search can find, read `low`. Now, after the contradicted and mixed rule (unchanged), unverified claims raise the band: when they are at least half of the verdicts the band is at least `high`, and any unverified claim makes it at least `medium`. They never lower a band. A scan with no claims still reads `low`. Every path that reports the scan's `overallRisk` uses the same rule from one function: quick scan, full scan, `POST /scan`, `/scan/stream`, `/scan/deep`, `/scan/batch`, consensus and the MCP `verify_claims` tool. (`POST /scan/compliance/:template` reports a different `overallRisk`, the template's rule-severity rollup, which is unchanged.) Verdicts, sources, billing, quota counting and the claim meter are unchanged. Side effects: the mock provider cites no source, so a mock scan now reads `high`; `POST /scan/compliance-gate` on an all-unverified scan now fails (422), since it fails on high risk.
- **No definite verdict without a source, on any provider.** A `supported`, `contradicted` or `mixed` verdict with no source the reader can open (on Gemini, no grounding chunk with a web uri) is now returned as `unverified` with `noSourceAbstain: true` and a fixed explanation, on every single-provider path (scan, stream, deep, full scan, batch, report, admin verify, MCP); before, only a sourceless Gemini `contradicted` was. OpenAI and Claude single-provider verify never cite a source, so their verdicts now always read `unverified`, as do the mock provider's. Such a claim is not billable and is not counted toward the scan quota or the claim meter; prompts, models and the sources kept when there are some are unchanged. A source counts only when its uri is an absolute http or https URL; any other source is dropped from the verdict. A scheduled scan's notification leaves out `overallRisk` when its verdicts are Gemini-grounded, a failed compliance gate on grounded verdicts sends only `{scanId, projectName, status, grounded}`, and error text sent to a caller's URL loses any Google grounding Link and is capped at 300 characters. `POST /webhooks/test/:id` works only for the webhook's owner or an admin key, and `GET /webhooks/test/history` is admin only. Webhook responses no longer show the owner's key id. Every scan result that fires `scan.complete` now carries a `scanId`, returned to the caller and named in the minimal event. A key lists and deletes only its own scheduled jobs (`GET /jobs`, `DELETE /jobs/:id`; admin keys, all), and a job's own `webhookUrl` gets nothing once its creator's key is deleted, disabled or expired; notifications to such a key stop too. Error text sent to a caller's URL is Faultline's own message or a fixed `Scan failed (provider error).`, never provider output. A retry stops once its webhook is deleted, and the weekly summary goes to each subscriber with only its own key. A schedule's own `webhookUrl` (accepted and SSRF-checked before, but never sent to) now gets each run's `scan.completed` or `scan.failed` event, under the same rules: only while the owner key is live, grounded results as counts, sanitized error text, no notify email. `GET /jobs/:id/progress` (bulk scan progress: filenames, per-file risk, errors) needs a key and answers only the key that created the job (admin: any); it had no key check. (emma-soul al:3dd437daabb68ad9, GoPMO 1.18.11.3; review findings from a codex fresh exec and a transcript-blind Opus seat)

- **`/scan/deep` no longer follows Google grounding Links, and honours robots.txt.** Its source check HEAD-probed every cited URL and followed redirects, so for a Gemini scan it followed each grounding Link to the publisher page, which Google's terms forbid ("using Links to identify destination pages for crawling or scraping"; emma-soul ruling al:07b45f0562efbbf0). A grounding Link is now never requested and its `evidenceLinks` entry carries `notChecked: "provider_terms"`; other sources ask the site's robots.txt before each hop (`notChecked: "robots"` when disallowed) and send `FaultlineEvidence/1.0 (+https://faultline.nxtg.ai)` instead of `Faultline-EvidenceBot/1.0`. The grounding-host check now also matches the host spelled with a trailing root dot (or `%2e`), which had got past an exact compare in the evidence, robots.txt and deep-scan paths. (GoPMO 1.18.11.3)
- **The JSON `/scan` cache is per caller, says when a hit was checked, and never holds Gemini Grounded Results.** The cache was keyed only by text, provider and cap, so one caller's 24-hour-old verdicts were served to another with only an `X-Cache` header. A result is now served back only to the caller that ran it (API key, and the forwarded user behind faultline-web's server key); a hit carries `cache: {hit: true, checkedAt}` in the body. A Gemini-grounded result is not cached at all, since Google's terms say "will not ... cache ... Grounded Results" and show them only "to the end user who submitted the prompt"; with the default provider every scan now runs fresh. A server-key request without a valid forwarded user ref is not cached, since it could be any web user. `/scan/deep` follows the same rules. The admin cache warm-up is retired: with per-caller entries a warmed result would be served to no one, so `POST /cache/warmup/run` and `POST /cache/warmup/:id/run` now answer 410 `cache_warmup_retired` and scan nothing. (emma-soul al:193832a732e0b82e item 7, GoPMO 1.18.11.3)
- **Provenance cannot be claimed by the provider.** `retriever`, `verifiedAt` and `retrievedAt` are now bound where the engine calls the provider, never taken from the provider's reply; the `gemini-grounding` retriever comes only from the built-in `gemini` provider or a consensus run whose shared retriever is Gemini grounding. Before this, a provider could label its verdict `gemini-grounding` with a backdated time and so exempt its own citations from the evidence fetch (shown by the EP4 examiner's spoof probe). (emma-soul al:193832a732e0b82e item 5, GoPMO 1.18.11.3)
- **A failed claim extraction is now reported, never hidden.** Every provider (Gemini, OpenAI, Claude, Perplexity) caught extraction errors and returned no claims; the scan then filled one synthetic claim per sentence, verified those and reported a normal result, and a full-scan estimate priced them. Measured 2026-10-13: two 150,000-character documents failed extraction (JSON cut off) yet reported 945 and 1,049 "claims" (docs/research/data/extraction-cost/README.md). Extraction now throws a typed error; `/scan` and `/scan/full/estimate` answer `502 {"error":"extraction_failed","reason"}`, `/scan/stream` sends the same fields in its error event, `/scan/batch` marks the item, the CLI exits 1 with a plain message and the MCP tool returns an error. A model that genuinely finds no claims still returns an empty list. Every claim the model returns is checked (non-empty text and id, a type of fact, opinion or interpretation, an integer importance 1-5); one malformed item fails the extraction as `invalid_output` instead of being padded with synthetic claims (codex E1). The `/scan` failover chain no longer falls back to the `mock` provider, which would have answered a real failure with invented "supported" verdicts; `mock` runs only when asked for.
- **A scan no longer cuts a sentence at the period in a case citation or abbreviation.** The step that makes sure every sentence gets at least one claim split text at every ". ", so "Delmont v. Arcadia Freight Systems, Inc., 947 F.3d 1182 (9th Cir. 2020)" became fragments, and the fragment ending "in Delmont v." was verified on its own and came back supported against an unrelated case. Sentences now end only before a capital letter, and not after "v.", "Inc.", "Cir.", "Supp.", other common abbreviations, initials or "U.S.". Reported by ce from an Evidence Watch proof run.
- **Gemini scan cost is priced at Gemini 2.5 Flash rates** ($0.30 input, $2.50 output per million tokens) in the provider-spend ledger and cost telemetry, the model the engine calls. It was priced at $0.15/$0.60.
- **A quick scan whose provider throws on every retry is now marked degraded and is never cached.** The claim came back as a plain "unverified" verdict with no `apiError`, so `verificationErrors` stayed 0, `degraded` stayed false, and the scan cache (which refuses only results with `apiError`) could serve the failure for 24 hours. Found while building the full scan, which already flagged it.
- **Admin benchmark batches no longer count as managed scans in `/costs/percentiles`.** Each `POST /admin/verify-claims` batch of up to 25 claims was recorded as one enterprise scan, so the live enterprise p50 of $0.884 was 25 claims at about $0.035 each. Batches are now tagged `kind: "admin-verify"` in the cost store and scan-cost log, are left out of the percentiles, and are no longer sent to the telemetry Worker; they still count in the provider-spend ledger. - **`GET /costs/percentiles` keeps its history across deploys and reports latency.** It reloads the scan-cost log at startup, adds `latencyMs` p50/p90/p99, and takes `?tier=` to read one plan's scans.
